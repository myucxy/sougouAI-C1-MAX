# C208 增强 Rec 与启动失败恢复方案

日期：2026-11-22。对象：原始 8MiB 镜像与 V0141。此文区分原生代码验证结果与尚未实现的设计。

## 已验证的原生行为

- 正常系统可以先调用启动槽查询，再调用原有启动切换 helper，将 OSB 的启动优先级置于 OSA 之前。软件回放不经过 OTA 拆包，元数据由原函数更新并通过原生校验。元数据记录位于 SPI 的 0x6000；它包含 A/B 优先级、重试次数、成功标记与校验值，不能只改一个字节。
- 目标 Rec 的重试次数和成功标记均无效时，原切换 helper 会拒绝。本次未尝试绕过该保护。
- 原始 SPL 的选槽、无效槽归一化和减计数机器码执行：A 设为未确认、3 次试启动，B 设为有效恢复系统，在每次未确认失败后发生复位的模型下，连续选择 A、A、A、B。镜像加载、元数据读写及复位端点为模型。
- 原主系统在 rt_init_thread_entry（0x180865f8）中调用成功确认（0x18060ff8）。该路径在组件初始化返回后确认系统成功，没有另外检验持续的 UI 响应。不能把此标记等同于界面、触摸和录音全部正常。
- 原 Rec 的 ota_main 在无可用升级包/更新失败的已测分支中，会根据主系统的启动记录尝试选回 A，或请求 MaskROM 并重启。它没有在这些分支中提供常驻的 USB 投包菜单。此处执行了原生分支，升级失败、槽查询与复位/MaskROM 端点为模型。

原生回放工具 `inspect_recovery_extension.py` 及其历史依赖保留于本地历史归档；精简公开仓库仅包含结果，不声称可以在没有那些输入时重新运行该回放。
结果：本目录 native-replay.json；原反汇编与完整执行环境保留于本地历史归档。

## 建议实现的恢复行为（尚未实现）

1. 进入主系统前，将本次启动置为待确认，并从尽可能早的可靠阶段启动硬件看门狗。
2. 主系统进入主页、UI 线程持续响应且必需的存储初始化成功后，才确认启动成功。离线开机不以服务器连接成功作为条件。
3. 启动失败由看门狗复位，下一次引导继续消耗试启动次数；达到阈值后选择 Rec。升级后的未确认试启动可利用现有计数。要覆盖已经成功启动过的版本在后续冷启动时发生故障，还需每次启动重新布置待确认状态，而不是只在 OTA 后设置一次。
4. 界面线程卡死但喂狗线程仍运行时，单靠现有独立喂狗并不能触发复位。喂狗条件应联系主系统健康状态。若故障发生在看门狗实际生效之前，覆盖范围仍是未知，需启动阶段或引导层配合验证。
5. Rec 不因没有包就返回损坏的主系统，也不自动重复刷同一份失败包。它应停留在恢复界面，显示进入原因，等待 USB 投包或用户选择备份恢复。
6. 恢复失败仍停留 Rec；只有完成镜像校验、写入和写后验证，才安排主系统试启动。不能在启动失败后备份损坏镜像并覆盖唯一的已知有效备份。

## USB 投包与备份（待移植、编译、实机验证）

SDK 参考 recovery_defconfig 已包含 USB device mass storage 配置及 eMMC/FAT 文件系统基础。该配置不是本机已经开启 USB 磁盘功能的证据。当前原厂 Rec 的 USB 枚举与磁盘读写尚未实测。

建议 Rec 支持：USB 连接电脑后复制升级包；电脑安全推出后，由 Rec 独占文件系统并完成校验、升级；导出 SPI 原始镜像和校验信息；选择已验证的旧镜像恢复；查看版本和上次失败原因。电脑通过 USB 写盘期间，Rec 不同时以文件系统方式写同一卷；备份或刷写时不向电脑提供可写的同一存储卷。

备份应在破坏性写入之前完成，写入临时文件、刷新并关闭、重新读取检查长度与校验，再成为有效备份。原始全片包含启动区、vendor/启动元数据、OSA、OSB 和 DSP；音乐、录音及机内文件系统中的身份配置需要另行保留。恢复本机元数据/身份需与版本切换规则兼容，不能把所有旧字段不加判断地覆盖。

Rec 分区为 524288 字节，原有效镜像（含头和 hash）242760 字节，后部有 281528 字节零填充。这只是 Flash 容量余量；USB 和界面代码、运行 RAM、栈与缓冲仍需编译和设备验证。

## 首次安装的关键边界

普通本地 OTA 当前写 OSA/DSP，不更新 OSB。把新 Rec 放进原 OTA 文件不会自动安装到 Rec 分区。

首次部署增强 Rec 需要独立验证的安装流程，且首次破坏性写入前已经取得本机原始备份。仅在增强 Rec 装好后才备份，无法保存被替换掉的原 Rec。桌面的 sg-bak.bin 与工程原始镜像逐字节一致，但不能据此证明现场每台设备的身份/元数据相同。

由于 Rec 是现有恢复基础，改坏它会缩小可用恢复范围。当前本机底层 USB 下载、断电后的进入方法和完整回写通道尚未完成验证。因此本次没有改写 Boot、分区、Rec 或 V0141 OTA，也没有生成供刷机的新 Rec 包。

## 验证边界

这是原始 ARM 指令与受控端点结合的软件回放，不是实体启动、USB 枚举、Flash 断电或故障恢复实验。通过的场景证明原生启动控制可作为实现基础；增强 Rec、启动健康监测和安装流程仍属于待实现、待验证项。
