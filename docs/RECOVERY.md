# Recovery 现状与规划

V0141 保留原 OSB Recovery，没有安装增强 Rec，也没有增加镜像备份或自动故障恢复功能。

## 已确认的基础

| 分区 | 文件偏移 | 大小 | 用途 |
| --- | --- | --- | --- |
| vendor | 0x001000 | 28KiB | 设备信息与启动控制记录，控制记录访问 0x6000 |
| IDBlock | 0x010000 | 64KiB | SPL 引导 |
| OSA | 0x020000 | 7MiB | 主应用 |
| OSB | 0x720000 | 512KiB | 独立恢复／升级程序 |
| dspext | 0x7a0000 | 384KiB | DSP 扩展 |

OSA 与 OSB 是主系统和恢复系统，不是两份完整主应用。普通本地 OTA 使用正常系统拆包、设置启动记录，再进入 OSB；观察到的恢复写入针对 OSA／DSP，当前路径不安装新的 OSB。

原生 ARM 指令的软件回放已验证：先读取启动记录，再使用原有 helper 可以选择 Rec；未收到成功确认且每次能复位时，三次主系统试启动之后可选择 Rec。启动控制含优先级、重试次数、成功标记和校验值，不应只写一个所谓启动字节。

这些结果的 Flash、镜像加载和复位端点是模型。没有对实体机器进行黑屏恢复、USB 枚举或破坏性断电验证。

## 为什么现在还不能保证自动恢复

原主系统在初始化线程中确认启动成功，没有在该路径额外等待持续的界面健康信号。程序校验正确但随后卡死，不一定耗尽启动尝试。独立喂狗线程若继续运行，也不能据此判断界面正常。

原 Rec 在所测无有效升级包／更新失败的路径中，可能选回 A 或请求 MaskROM 后重启，而不是停留为电脑提供 USB 投包界面。SPL 的硬件升级检测分支也没有对应到已验证的机身组合键。

## 尚未实现的增强方案

- 由主系统菜单手动请求下次启动 Rec。
- 从可靠的早期阶段启动硬件看门狗；主页与必要存储持续健康后才确认启动成功。
- 连续启动失败后进入 Rec；要覆盖日常冷启动故障，需每次重新布置待确认状态，不能只保护 OTA 后首次启动。
- Rec 在没有包时常驻等待；USB 连接电脑后复制升级包，安全退出 USB 后校验并刷写。
- 在破坏性写入之前分块导出原始镜像、刷新落盘、重新读取核验；保留已知有效备份。
- 从有效备份恢复失败则继续留在 Rec，避免反复启动损坏系统或反复刷同一坏包。

USB 可写磁盘与设备本地文件系统不能同时无协调地写同一卷。硬件看门狗的生效时机、早期死机覆盖、USB 驱动、按键和断电一致性都需要本机验证。Rec 剩余约 275KiB Flash 不是运行 RAM 余量。

首次安装增强 Rec 需要独立验证的写入流程；普通 OTA 当前不会更新它。首次写 Rec 前就应已有原始备份与底层恢复条件，不能等替换完原 Rec 才保存“原系统”。
